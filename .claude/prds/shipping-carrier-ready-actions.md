# PRD: shipping-carrier-ready-actions

## Executive Summary

发货工作台把顺丰和菜鸟拆成两个独立处理入口。每个入口分别展示地址待审核、地址已审核和运单待回填数量；只有包裹资料、地址二审、运单冲突检查和对应物流接口能力全部通过时，入口与弹窗中的下单按钮才显示为绿色，并由运营人员明确点击后提交真实订单。

## Problem Statement

现有发货提醒只有一个“处理下一单”按钮，顺丰和菜鸟混在同一队列。弹窗下单按钮虽然会被禁用，但没有清楚区分“检查通过，可以真实下单”和“只能打开平台人工处理”，容易误判当前状态。

## User Stories

- 作为发货运营人员，我希望顺丰和菜鸟分开显示，以便按承运商处理包裹。
  - 验收：发货提醒同时显示两个独立承运商卡片和各自数量。
- 作为发货运营人员，我希望绿色按钮只代表可以真实下单。
  - 验收：地址未二审、包裹条件不完整、已有/冲突运单、接口未接通或缺少授权码时均不显示绿色。
- 作为发货运营人员，我希望点击绿色按钮后先进入对应包裹复核，再由弹窗中的绿色按钮明确提交。
  - 验收：主页面绿色按钮打开同一承运商的可下单包裹；不会自动产生物流订单。

## Functional Requirements

1. 发货提醒按顺丰、菜鸟分别汇总包裹状态。
2. 每个承运商入口显示地址待审核、地址已审核、运单待回填数量。
3. 对应承运商存在地址已审核包裹且真实接口和本次授权均就绪时，显示绿色“检查通过，点击下单”按钮。
4. 接口未就绪时保持普通按钮并说明需要接通接口或人工处理，不得显示为绿色可下单。
5. 弹窗内再次执行包裹、地址、运单和接口检查；全部通过后才把真实下单按钮改为绿色。
6. 点击主页面绿色按钮只打开复核弹窗；只有点击弹窗内绿色按钮才调用真实物流下单接口。

## Non-Functional Requirements

- 不创建演示物流订单或假运单号。
- 不在自动化回归中调用真实下单接口。
- 保留现有人工录入真实运单号、回填和包裹合并流程。

## Success Criteria

- 浏览器回归覆盖顺丰可下单、菜鸟接口未接通、地址未二审三种状态。
- 绿色状态与按钮可用状态完全一致。
- 现有完整测试全部通过，公网部署后完成只读回归检查。

## Out of Scope

- 不新增菜鸟 API 凭据或改变现有物流网关配置。
- 不自动提交订单，不批量跳过人工复核。
- 不修改顺丰/菜鸟的费用、承运商自动判断阈值和取消订单流程。
